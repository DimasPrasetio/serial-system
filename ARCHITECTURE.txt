================================================================================
1) TUJUAN SISTEM
================================================================================

Serial System adalah backend license server + admin panel untuk:
- Mengelola aplikasi yang dilisensikan.
- Mengelola paket lisensi (trial dan paid).
- Membuat serial activation / renewal sesuai pesanan user.
- Menangani aktivasi trial, aktivasi paid, perpanjangan, cek status, dan manajemen device.
- Menyediakan kontrol admin berbasis role/permission.

Model bisnis yang diimplementasikan saat ini:
- User memesan ke admin di luar aplikasi.
- Admin membuat serial pesanan di menu `Kode Aktivasi`.
- Admin memberi serial tersebut ke user (di luar aplikasi).
- User memasukkan serial di desktop app saat aktivasi paid.
- Trial dilakukan tanpa serial (input user hanya email, metadata device dikirim app).

5) DOMAIN MODEL DAN ATURAN BISNIS
================================================================================

5.1 Application
- Tabel: `applications`
- Kunci: `code` unik
- Bisa aktif/nonaktif (`is_active`)
- Bisa memakai application token (`token_hash`, `token_encrypted`)
- Jika `token_hash` terisi, header `X-Application-Token` wajib valid

5.2 Plan
- Tabel: `plans`
- Terikat ke application
- Properti inti: `term_days`, `seat_limit`, `is_trial`, `is_active`
- Trial dan paid dipisahkan lewat `is_trial`

5.3 SerialNumber
- Tabel: `serial_numbers`
- Tipe: `initial` (aktivasi baru), `renew` (perpanjangan)
- Status: `available`, `used`, `void`
- Secret storage:
  - `serial_hash` (validasi)
  - `serial_encrypted` (reveal di admin UI)
  - `serial_last4` (display masked)
- Metadata order: `customer_email`, `order_note`

5.4 License
- Tabel: `licenses` (UUID primary key)
- Status: `active`, `expired`, `revoked`
- Relasi ke account, plan, application, issued serial (opsional)
- Masa berlaku: `starts_at_utc`, `expires_at_utc`

5.5 DeviceBinding
- Tabel: `device_bindings`
- Unik per (`license_id`, `fingerprint_hash`)
- Status device: `active` / `inactive`
- Dipakai untuk enforcement seat limit

5.6 TrialClaim
- Tabel: `trial_claims`
- Unik per (`application_id`, `device_hash`)
- Membatasi trial 1x per device per application

5.7 LicenseToken
- Tabel: `license_tokens`
- Token plaintext dibuat sekali (`tok_` + random), disimpan hash
- Expired default 30 hari dari issue

5.8 Admin + Permission + Audit
- Admin auth di tabel `admins`
- Role/permission via spatie tables
- Audit log ke tabel `audit_logs` untuk aksi penting tertentu

================================================================================
11) FLOW BISNIS END-TO-END
================================================================================

11.1 Flow A - Admin membuat serial pesanan user
1. Admin membuka menu `Kode Aktivasi`.
2. Admin memilih Application + Paket paid + jenis serial (aktivasi/perpanjangan).
3. Admin isi email user dan catatan pesanan.
4. Sistem generate serial plaintext, simpan:
   - hash untuk validasi API
   - encrypted untuk reveal
   - metadata order
5. Admin melihat daftar serial dalam format masked.
6. Admin klik `Lihat Serial` jika perlu melihat/copy serial asli.
7. Serial asli diberikan ke user di luar aplikasi.

11.2 Flow B - Trial activation
1. Client kirim `email + device`.
2. System cari plan trial aktif di application terkait.
3. Cek `trial_claims` (application + device) agar 1 device hanya trial sekali.
4. Buat account (jika belum ada), buat license trial, bind device.
5. Issue API token baru.
6. Return payload license + `api_token`.

11.3 Flow C - Paid activation (serial initial)
1. Client kirim `serial + email + device`.
2. System validasi serial initial:
   - hash cocok
   - application cocok
   - status bukan void
   - plan bukan trial dan aktif
3. Jika serial `available`:
   - create account
   - create license
   - mark serial `used`
4. Jika serial sudah `used`:
   - hanya boleh dipakai email yang sama dengan owner license
   - email beda -> `SERIAL_EMAIL_MISMATCH`
5. Cek seat limit:
   - jika device baru dan seat penuh -> `SEAT_LIMIT_REACHED`
6. Bind device aktif (create/update)
7. Issue API token
8. Return license summary + token

11.4 Flow D - Renewal (serial renew)
1. Client kirim `renew_serial` dengan bearer token license.
2. System tolak jika license revoked.
3. Validasi serial renew:
   - status available
   - application cocok
   - seat_limit plan renew harus sama dengan license aktif
4. Hitung expiry baru:
   - base = max(now, expiry lama)
   - expiry baru = base + term_days plan renew
5. Update plan_id license ke plan renew dan mark serial renew jadi used.

11.5 Flow E - Device management
- Deactivate:
  - validasi device aktif pada license
  - ubah status ke inactive + set deactivated timestamp
- List devices:
  - return semua binding dengan status (`deactivated` untuk inactive)
  - return `seat_limit` dan `seat_used`

11.6 Flow F - Status check
1. Bearer token diverifikasi.
2. Jika license revoked -> `LICENSE_REVOKED`.
3. Jika expiry lewat:
   - status lisensi disinkronkan ke `expired` bila perlu
   - return `LICENSE_EXPIRED`
4. Jika valid -> return status + days remaining + seat usage.

================================================================================
13) PENGELOLAAN SECRET DAN KEAMANAN DATA
================================================================================

13.1 Secret handling
- Serial activation:
  - disimpan sebagai `serial_hash`
  - plaintext tidak disimpan langsung
  - reveal menggunakan `serial_encrypted`
- Application key:
  - validasi pakai `token_hash`
  - reveal key memakai `token_encrypted`
- API license token:
  - hanya hash yang disimpan
  - plaintext token hanya diketahui saat issue response

13.2 Headers dan anti mismatch
- Header application wajib di semua route lisensi.
- Token lisensi harus berasal dari application yang sama.

13.3 Cache control untuk reveal
- Endpoint reveal token/serial memberi header no-store/no-cache.
